# 日志与业务库查询

项目：rag-databrain  
更新：2026-10-24

只读账号是数据库和 CLS 上的权限，不是让模型变稳的办法。模型进程不拿这些账号。

三道门，缺一不可：

1. **谁能查。** 身份来自登录，不来自请求体里的字段。发给模型的 `tools` 按角色裁剪。业务的请求里没有日志工具和库工具，模型无从调用。
2. **这轮查什么。** 规则先判，判不出再走现有的 `_route`。输出本轮渠道：知识库、日志、业务行。渠道和角色取交集。不在交集里的工具，这轮不发给模型；模型若仍调用，代码回「这轮不查」，不打到后端。
3. **怎么查。** 独立的 MCP 服务持有只读账号，走 HTTP。Agent 只做客户端。腾讯云 CLS 和小公司的 SQL 是这个服务内部的两种后端，工具名不变。

## 需求理解

要做：

- 角色三种：`dev`（开发）、`product`（产品）、`biz`（业务）。
- 角色工具：开发和产品是 `retrieve`、`search_logs`、`lookup_row`。业务只有 `retrieve`。
- 本轮渠道：`kb`、`logs`、`rows`。一次问题可以同时要知识库和日志。
- 工具参数仍是表单。`search_logs(window, service, level, keyword)`，`lookup_row(view, key)`。`window` 只允许 `15m`、`1h`、`6h`、`24h`、`7d`。`level` 只允许空、`ERROR`、`WARN`、`INFO`。`view` 枚举来自配置。
- 路由已经填好的窗口、服务、单号，由代码写进第一次调用。模型和用户都不能改成另一张表或另一段查询语句。
- MCP 传输用 HTTP（`OPS_MCP_URL`），不用 stdio。stdio 只适合本机 IDE。服务之间要能分开部署。
- 有记录才写入 `sources`。空结果、超时、无权限都不让模型用自身知识编一条日志或一个订单状态。
- 调用记一行审计：谁、角色、工具、参数、条数、耗时。不记日志正文。

不做：

- 不在 `AskIn` 里加 `role`。调用方自己填的角色不算数。
- 不把 CLS 密钥或数据库密码放进 Agent 进程和提示词。
- 不向模型提供「执行这段 SQL」或「执行这段 CLS 语句」的工具。只读账号挡不住 `SELECT` 扫全表，也挡不住把不该看的列送进模型。
- 不把日志和业务行写入 `documents` / `chunks`。
- 不改知识库检索的排序。`retrieve` 仍走 `store.py`。
- 不上进程沙箱。MCP 工具不执行命令、不写文件。
- 不做 Loki、Elasticsearch，也不做视图以下的列级权限。以后产品不能看某张视图时，只按角色裁 `view` 枚举。
- 不把 MCP 端口暴露到公网。这层信任 Agent 已经做过角色判断。Agent 被攻破时，损失停在只读范围。

复用：

- `stream_ask` 的循环、未知工具回一条结果、最后一轮禁止工具、相同参数不重复打。
- `_route` 的 JSON 解析失败就退回原循环。日志和业务行在解析失败时退回只查知识库，不开实时查询。
- 消歧仍只反问一个缺口。缺服务名或缺单号时用这条，不猜。
- `rank.py` 里错误码的字符形态（`[A-Za-z]{1,6}` 加数字）用于发现「要查日志」。不把 `rank.py` 的排序函数拿来查库。
- `MAX_CONTEXT_CHARS`、`MAX_AGENT_STEPS`。知识库存储仍只经过 `store.py` / `storage.py`。

### 谁能查

| 角色 | 知识库 | 日志 | 业务行 |
|---|---|---|---|
| 开发 `dev` | 能 | 能 | 能 |
| 产品 `product` | 能 | 能 | 能 |
| 业务 `biz` | 能 | 不能 | 不能 |

身份只在 FastAPI 依赖里解析。生产环境校验本公司的登录令牌，用组名映射角色（`ROLE_MAP`）。没配登录签发方时，默认角色是 `biz`。本机在 `.env` 设 `DEV_ROLE=dev` 才能用开发权限。`DEV_ROLE` 在配了签发方之后无效。

业务问到线上情况时，代码直接回：「线上日志和业务记录只有开发和产品可以查。」这句不是模型生成的。问题里还有制度、流程，才继续 `retrieve`。纯看日志、纯查一笔单，到此结束，不调用模型编造。

### 这轮查什么

先跑规则，命中就不再请模型做渠道判断。

| 问句里有 | 渠道 | 钉死的参数 |
|---|---|---|
| 订单号、单号，或一串「字母前缀 + 至少 6 位数字」 | `rows` | `key` 用命中的那串。视图只有一个时钉死 `view`，否则反问要查哪一种 |
| 错误码，或「报错 / 异常 / 超时 / 5xx / trace / request_id / 日志」 | `logs` | 错误码写入 `keyword`。`刚才`/`刚刚` → `15m`，`今天` → `24h`，`最近` → `7d`，都没有 → `1h`。`报错`/`异常`/`超时` → `ERROR` |
| 上面任一，并且还有「文档 / 制度 / 怎么办 / 怎么处理」 | 再加 `kb` | 实时查询的参数仍按上一行 |
| 都没有 | 交给 `_route` | 模型只输出 JSON：`need` 是 `kb`、`logs`、`rows` 的子集，外加原来的 `query` 或反问 |

`_route` 解析失败，或 `need` 里出现不认识的值：本轮只留 `kb`。

然后取交集：

- 本轮实际渠道 = 路由渠道 ∩ 角色允许的渠道。
- `retrieve` 只在实际渠道含 `kb` 时出现。开发问「年假几天」不会带上 `search_logs`，避免顺手打到线上。
- 实际渠道含 `logs` 或 `rows` 时，进入生成前先执行一次对应工具，参数用上面钉死的值。模型后面可以在步数内改 `keyword` 再查一次，不能改窗口、服务、视图和主键。
- 模型调用了本轮没有的工具：工具结果是「这轮不查日志」或「这轮不查业务记录」，MCP 不收到请求。

四个例子：

- 业务：「刚才订单服务报 E07」。规则命中日志。交集为空。固定拒绝，不调 MCP，不让模型描述日志。
- 开发：「年假几天」。无实时信号，路由得到 `kb`。这轮工具只有 `retrieve`。
- 产品：「订单 AB123456 现在什么状态」。规则命中业务行。先 `lookup_row`。没有这一行就回不知道，不编状态。
- 开发：「E07 文档里怎么处理，线上最近有没有」。渠道是 `kb` + `logs`。先查日志，循环里再 `retrieve`。两份都算证据。

### 怎么查

MCP 服务进程名 `ops`，入口 `python -m rag_databrain.ops_server`。Agent 用官方 MCP Python 客户端连 `OPS_MCP_URL`，带 `OPS_MCP_TOKEN`。依赖加在步骤 3。

服务对外只有两个工具，参数即上面的表单。服务端把表单编成 SQL 或 CLS 语句。`keyword` 只作词项，不拼进查询语法。

| 环境变量（只在 MCP 进程） | 作用 |
|---|---|
| `OPS_BACKEND=sql` | 小公司。日志和业务行都走 SQL |
| `OPS_BACKEND=cls` | 大公司日志走 CLS。业务行仍走 SQL，所以同时还要 `DATA_DATABASE_URL` |
| `LOG_DATABASE_URL` | 只读账号的连接串。`default_transaction_read_only=on`，语句超时 3 秒 |
| `LOG_TABLE` | 日志表。列固定为时间、级别、服务、正文、`request_id` |
| `DATA_DATABASE_URL` | 业务库只读账号。可与日志不是同一台库 |
| `DATA_VIEWS` | `orders:id,refunds:refund_id` 这种「视图:主键列」 |
| `LOG_SERVICES` | 允许的服务名。只有一个时自动钉死，多个又没说服务名就反问 |
| `CLS_REGION` / `CLS_TOPIC_ID` / `CLS_SECRET_ID` / `CLS_SECRET_KEY` | 只在 `OPS_BACKEND=cls` 时读取 |
| `CLS_TOPIC_NAME` | 写进出处的短名，例如「订单主题」。不把 TopicId 回给用户 |

SQL 账号的授权是 `GRANT SELECT` 到那张日志表和那些视图，没有插入、更新、删除。CLS 的 CAM 只有 `cls:SearchLog`，资源只到这一个主题。

返回给模型的正文是截断后的纯文本：时间、级别、服务、一行消息、`request_id`，或业务视图的少数列。开头写「共 N 条，已截断」。默认 20，上限 50。超时回「查询超时」。来源标签：`sql:日志表名`、`view:视图名`、`cls:主题短名`。

## 步骤

| ID | 做什么 | 主要文件 |
|---|---|---|
| 1 | 从登录令牌解析角色。业务的补全请求里不放日志和库工具。无权限的实时问题用固定句子结束。 | `src/rag_databrain/principal.py`、`src/rag_databrain/main.py`、`src/rag_databrain/graph.py` |
| 2 | 规则和 `_route` 产出本轮渠道，和角色取交集。参数能钉死的先钉死。缺一个槽位就只反问那一个。 | `src/rag_databrain/graph.py` |
| 3 | Agent 作为 MCP 客户端，只转发交集里的调用。先接一个固定返回的本地服务，用来把循环和证据门跑通。 | `src/rag_databrain/ops_mcp.py`、`src/rag_databrain/ops_server.py`、`src/rag_databrain/graph.py`、`pyproject.toml` |
| 4 | MCP 的 SQL 后端。只读账号、参数化查询、视图名单。 | `src/rag_databrain/ops_server.py`、`.env.example` |
| 5 | MCP 的 CLS 后端，工具名和参数与步骤 4 相同。CAM 只有 `SearchLog`。 | `src/rag_databrain/ops_server.py`、`.env.example` |

步骤 1 和 2 不连接任何日志源。步骤 3 不读真实库。这样角色裁剪和渠道判断可以单独验证。4 和 5 可以合并成一次「接上真实后端」，1、2、3 不要并进去。

## Step 1 commit

```text
feat: 按登录身份裁剪工具，业务用户的请求里不出现日志和库查询。
```

做完时：

- 请求体里没有角色字段。令牌映射为 `dev`、`product`、`biz`，映射失败回 401。
- 未配置签发方时角色是 `biz`。`.env` 里的 `DEV_ROLE` 只在未配置签发方时生效。
- `stream_ask` 收到允许的工具名集合。`biz` 的集合只有 `retrieve`。
- `biz` 问「看一下刚才的报错」：不调用模型，回答是固定句子「线上日志和业务记录只有开发和产品可以查。」
- `biz` 问「报销怎么走，另外看一下线上报错」：固定句子加上原有的知识库回答。回答里不能出现编造的日志行。

## Step 2 commit

```text
feat: 由规则和路由决定本轮查知识库、日志还是业务记录，模型不能自行扩大渠道。
```

做完时：

- 「刚才订单服务报 E07」得到 `logs`、窗口 `15m`、关键字 `E07`。服务名在 `LOG_SERVICES` 里只有一个就钉死，有多个且问句没点名就只反问「哪个服务？」。
- 「订单 AB123456 现在什么状态」得到 `rows` 和主键。视图多于一个且问句对不上名称时，只反问要查订单还是退款，不查。
- 「年假几天」得到 `kb`。发给模型的工具列表里没有 `search_logs` 和 `lookup_row`。
- 「E07 文档里怎么处理，线上最近有没有」得到 `kb` 和 `logs`。
- `_route` 吐了非法 JSON：只留 `kb`。
- 模型调用本轮没有的工具时，工具结果是「这轮不查日志」或「这轮不查业务记录」。

这一步仍不访问 MCP。渠道结果先记在状态里，下一步才执行。

## Step 3 commit

```text
feat: 经只读 MCP 执行日志和业务查询，调用失败只回工具结果。
```

做完时：

- `pyproject.toml` 增加 MCP 客户端依赖。新增 `python -m rag_databrain.ops_server`，用 HTTP 提供两个工具。此步的服务不连数据库，按参数回一条固定样例，或在未配置后端时回「日志源未配置」「业务库未配置」。
- Agent 只把「角色允许且本轮渠道包含」的调用转发出去。转发前用服务端钉死的窗口、服务、视图、主键覆盖模型参数。
- 实际渠道含 `logs` 或 `rows` 时，生成前先执行一次，不依赖模型记得调用。
- 相同工具加相同参数不打第二次。超时和异常变成工具结果里的短句，SSE 不因此发 `error`。
- 有行才把来源标签追加进 `sources`。没有行时，最后一轮仍回不知道，不采用模型正文。
- 审计打一行：用户、角色、工具、参数、条数、耗时。样例正文不进这行。
- 开发问日志问题时，`sources` 里出现样例来源，回答只能根据样例。业务用户仍然停在步骤 1 的固定句子，MCP 访问日志里没有这个人。

## Step 4 commit

```text
feat: MCP 用只读 SQL 查日志表和业务视图，账号没有写权限。
```

做完时：

- `OPS_BACKEND=sql`。日志查询是参数化 `SELECT`，条件只有时间范围、服务、级别、关键字，`LIMIT` 不超过 50。
- `lookup_row` 的表名和主键列只来自 `DATA_VIEWS`，值用占位符。名单外的视图在 MCP 进程内再拒一次，不单靠 Agent。
- 连接使用只读账号。文档写明要执行的授权：日志表和这些视图的 `SELECT`，以及会话级 `default_transaction_read_only=on`、语句超时 3 秒。代码在每次连接上执行这两项设置。
- 表不存在或账号没有权限时，工具结果是「查询失败」，驱动的报错原文不进模型。
- `.env.example` 写上 MCP 进程的变量。Agent 的 `.env` 只有 `OPS_MCP_URL` 和 `OPS_MCP_TOKEN`。

## Step 5 commit

```text
feat: 日志 MCP 可改走腾讯云 CLS 检索，CAM 只允许 SearchLog。
```

做完时：

- `OPS_BACKEND=cls` 时，`search_logs` 调用 CLS `SearchLog`。语句由服务端拼成级别、服务名和关键字的与关系。关键字作为整词，不把用户原话拼接进查询语法。
- 时间用步骤 2 钉死的窗口换成毫秒起止。`Limit` 不超过 50。
- 密钥和 TopicId 只出现在 MCP 进程的环境变量里。Agent 仓库的运行环境没有这四项。
- CAM 策略写进文档：动作只有 `cls:SearchLog`，资源只有这一个主题。
- `lookup_row` 仍走步骤 4 的 SQL。没有 `DATA_DATABASE_URL` 时回「业务库未配置」，不去 CLS 里猜订单。
- 出处是 `cls:` 加 `CLS_TOPIC_NAME`，不是 TopicId。
- 签名用标准库。与官方接口对不上时再考虑 SDK，不在这一步先加上。

合并示例：合并 4 和 5。说「继续」或「做 step N」开始写。
