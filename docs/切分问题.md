# 文档切分

活文档。和当前解析对齐。选型表见 [architecture.md](architecture.md)。

## 一句话

Markdown 和有文本层的 PDF 抽成纯文本，再按 500 字、80 字重叠滑窗。整份几乎没有字的 PDF 按页渲染后做文字识别，再进同一条滑窗。标题、代码、表格、双栏仍不认。

## 面试里问得最多的

按场次，不是按难度。

几乎每次都会问前三题：

1. 块多大，要不要重叠。切太碎和切太长分别坏在哪。
2. 按长度切，还是按标题、段落、语义切。
3. PDF 怎么办：扫描件、双栏、页眉页脚、表格、跨页。

文档一具体到 Markdown 或制度 PDF，紧接着会问：

4. 标题被切开之后，小块还知不知道自己属于哪一节。
5. 代码块、表格从中间断开怎么办。
6. 答案引用能不能回到页码或章节，还是只能回到文件名。

会问，但通常是追问：

7. 小块用来检索、大块用来生成（父子块）。
8. 按字符还是按 token。中英混排时同一个数字差很多。
9. 重叠会让同一段出现两次，检索连着命中两块，上下文被同一句话占满。

## 现实里会坏的地方

### Markdown

一个标题下正文可能有几千字，按标题切完仍然超窗口；另一个标题下只有一句话，单独成块又没有信息。固定滑窗会把围栏代码、表格、有序列表从中间切开，后半段没有开头，检索能命中，生成对不上。

中文稿常把一段折成多行。按行切会把一句话拆开。切之前把换行压成空格，代码缩进和表格列也会一起没掉。

小块只剩「第三步」加半句，不知道是哪份制度的第三步。父标题没写进块里，向量对不上「年假怎么批」。图片和链接只剩路径，正文不在文件里。文首的 front matter、目录会变成和正文一样的块，检索被目录里的标题词带跑。

### PDF

扫描件和整页图片没有文本层，或者只有页眉。有文本层也不等于读序正确，双栏经常先横着读，左右栏拼成一句。

页眉、页脚、页码每页重复，向量被「内部资料」「第 n 页」拉偏。表格抽出来是一串被空格拆开的单元格，行和列没了，合并单元格更乱。一段话跨页时，页尾和下一页页首各留半句，中间还夹着页眉。

英文断词连字符、图注、脚注、水印会混进正文。中文 PDF 字体编码不对时，抽出的是乱码，但不是空字符串，会照样入库。块上没有页码，回答只能说文件名。

## 本仓库现在怎么处理

| 问题 | 现在 | 为什么停在这里 |
|---|---|---|
| 格式乱猜 | 只收 `.txt` `.md` `.pdf`，其余拒绝 | 猜格式会把二进制当文本切进去 |
| PDF 打不开 | 整份拒绝，不入库 | 损坏文件没有可检索的内容 |
| 图片页、扫描件没有文本层 | 平均每页不足 40 字就按页渲染，做文字识别 | 有正文的 PDF 不把里面的插图再识别一遍 |
| 识别完仍然没有字 | 整份拒绝，不入库 | 空白页没有内容 |
| Windows 中文 txt/md 是 GBK | 先按 UTF-8，失败再按 GBK | 只覆盖这两种文本编码 |
| 换行把同一句拆成很多空白块 | 切分前把连续空白压成一个空格 | 小文件上最常见的噪声；代价见下 |
| 句子正好切在窗口边上 | 500 字一块，相邻块重叠 80 字 | 字符窗口，不是 token，也不是句号 |
| 上传过大 | 超过 10MB 拒绝 | 避免整份读进内存再切 |
| 切出来的块塞不进模型窗口 | 检索按相关度从高往低装，超了丢掉后面的 | 这是装上下文，不是改切分 |

压空白是有意的交换：Markdown 的标题符号还在，换行、缩进、表格列没了。代码块和表格在这一步已经坏了，后面的滑窗只是再切一次。

PDF 先抽文本层。平均每页不足 40 个字，就当成图片或扫描件：按页渲染，用 RapidOCR 认中文和英文。识别出的字更多才换上，否则留下原来的文本层。然后走和 Markdown 同一条滑窗。有正文的文件里夹的图不会单独识别。文本层已经很长的乱码会照样入库，不会改走识别。双栏错序、页眉页脚只要抽得出字，也会入库。块上只留文件名和顺序号，没有页码，没有标题路径。

重叠没有去重。同一段的两个窗口都可能排进前几名，上下文被同一句话占两次。

## 明确留到以后

| 问题 | 触发再做 | 倾向 |
|---|---|---|
| 按标题切，小块带上父标题 | Markdown 问答经常命中「第三步」却对不上制度 | 先按标题切开，超长的节再滑窗，块首写上标题路径 |
| 代码块、表格不从中间切 | 这类块被引用时答案明显错 | 围栏和表格整段保留，超长再单独处理 |
| 双栏、表格、页眉页脚、长乱码文本层 | PDF 开始稳定答错，或文本层是乱码 | 换版面解析。架构里写的是 LlamaIndex |
| 引用到页 | 用户要核对原文页码 | 抽文本时带上页码，写进块 |
| 父子块 | 小块能搜到，生成缺上下文 | 检索用小块，生成换上该块所在的节 |
| 按 token 切 | 要和某一家模型的窗口对齐 | 再上 tiktoken；现在和装上下文一样按字符估 |
| 重叠块近重复 | 前几名经常是同一段的两个窗口 | 相邻高分块合并，或重叠部分不单独计为新证据 |

库还小、文件还是纯文本时，滑窗够用。不要为了面试题先把解析器换掉。

## 面试可以怎么说

块的大小是在「一条里要有完整事实」和「不要把无关句子嵌进同一个向量」之间取的。太长，问题只占块里一小段，相似度被冲淡。太短，事实被切成两半，哪一半都答不全。重叠是为了窗口边界上的那句话两边都还在。代价是同一段会存成两块，检索可能连着命中。

Markdown 和 PDF 的麻烦在抽文本的时候结构已经丢了。标题路径、表格行列、阅读顺序、页眉，都得在切分之前保住。

本仓库：有字的 PDF 抽文本层；整份几乎没字就按页渲染做文字识别。然后和 Markdown 一样压空白，500 字重叠 80 字。打不开、以及识别完仍没字的 PDF 直接拒绝。页码、标题、表格、双栏都还没有。开始答错再换解析。
