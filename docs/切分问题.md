# 文档切分

活文档。和当前解析对齐。选型表见 [architecture.md](architecture.md)。

## 一句话

先拆成段落、表格、图片、脚注块，再按种类切。正文超长才 500 字重叠 80 字滑窗；表格整段保留行列，跨页先拼再切。块首写标题路径和页码。扫描件用识别框还原阅读顺序，不把 OCR 字直接滑窗。

## 面试里问得最多的

按场次，不是按难度。

几乎每次都会问前三题：

1. 块多大，要不要重叠。切太碎和切太长分别坏在哪。
2. 按长度切，还是按标题、段落、语义切。
3. PDF 怎么办：扫描件、双栏、页眉页脚、表格、跨页。

文档一具体到 Markdown 或制度 PDF，紧接着会问：

4. 标题被切开之后，小块还知不知道自己属于哪一节。
5. 代码块、表格从中间断开怎么办。
6. 答案引用能不能回到页码或章节，还是只能回到文件名。

会问，但通常是追问：

7. 小块用来检索、大块用来生成（父子块）。
8. 按字符还是按 token。中英混排时同一个数字差很多。
9. 重叠会让同一段出现两次，检索连着命中两块，上下文被同一句话占满。

## 现实里会坏的地方

### Markdown

一个标题下正文可能有几千字，按标题切完仍然超窗口；另一个标题下只有一句话，单独成块又没有信息。固定滑窗会把围栏代码、表格、有序列表从中间切开，后半段没有开头，检索能命中，生成对不上。

中文稿常把一段折成多行。按行切会把一句话拆开。切之前把换行压成空格，代码缩进和表格列也会一起没掉。

小块只剩「第三步」加半句，不知道是哪份制度的第三步。父标题没写进块里，向量对不上「年假怎么批」。图片和链接只剩路径，正文不在文件里。文首的 front matter、目录会变成和正文一样的块，检索被目录里的标题词带跑。

### PDF

扫描件和整页图片没有文本层，或者只有页眉。有文本层也不等于读序正确，双栏经常先横着读，左右栏拼成一句。

页眉、页脚、页码每页重复，向量被「内部资料」「第 n 页」拉偏。表格抽出来是一串被空格拆开的单元格，行和列没了，合并单元格更乱。一段话跨页时，页尾和下一页页首各留半句，中间还夹着页眉。

英文断词连字符、图注、脚注、水印会混进正文。中文 PDF 字体编码不对时，抽出的是乱码，但不是空字符串，会照样入库。块上没有页码，回答只能说文件名。

## 本仓库现在怎么处理

| 问题 | 现在 | 为什么停在这里 |
|---|---|---|
| 格式乱猜 | 只收 `.txt` `.md` `.pdf`，其余拒绝 | 猜格式会把二进制当文本切进去 |
| PDF 打不开 | 整份拒绝，不入库 | 损坏文件没有可检索的内容 |
| 图片页、扫描件没有文本层 | 平均每页不足 40 字就按页渲染，识别框还原阅读顺序 | 有正文的 PDF 不把里面的插图再识别一遍 |
| 识别完仍然没有字 | 整份拒绝，不入库 | 空白页没有内容 |
| Windows 中文 txt/md 是 GBK | 先按 UTF-8，失败再按 GBK | 只覆盖这两种文本编码 |
| 标题切开后不知道属于哪一节 | 块首写标题路径；PDF 再加页码 | 解析器写路径，不另调模型写上下文 |
| 代码块、表格从中间断开 | 围栏和表格整段保留；表太长按行切并重复表头 | 行还在，列名不能只出现在第一块 |
| 跨页表、多级表头、合并格 | 列数相同且无新表题就拼；空格先下再右补；多级表头竖着拼 | 启发式，复杂版式不够再换 LlamaIndex |
| 表格检索对不上单元格 | 块里先写表格摘要（标题、列名、行数），再跟结构化表 | 摘要用来召回，表体用来对数字 |
| 双栏读序、页眉页脚 | 中间有沟才分栏，先左后右；多页顶端底端重复的丢掉 | 沟不明显的双栏仍可能横着读 |
| 图、脚注 | 图片块留下近旁图注和页内位置；页底编号行当脚注 | 不做视觉模型，图意只靠图注 |
| 句子正好切在窗口边上 | 只有超长正文才 500 字一块、重叠 80 字 | 字符窗口，不是 token，也不是句号 |
| 上传过大 | 超过 10MB 拒绝 | 避免整份读进内存再切 |
| 切出来的块塞不进模型窗口 | 检索按相关度从高往低装，超了丢掉后面的 | 这是装上下文，不是改切分 |

Markdown 按标题、围栏、管道表拆块，不再先把整份压成一行。PDF 有文本层时用 pdfplumber 抽词框和表；抽不到再退回按页纯文本。扫描件用 RapidOCR 的框，不把识别字直接空格拼接。旧库要重新上传才会变成结构块。

重叠没有去重。同一段的两个窗口都可能排进前几名，上下文被同一句话占两次。

## 三道进阶题

### 1. 非结构化、多模态、复杂版式，怎么保证解析后不丢语义？

这是版面理解加结构切分，不是换一个更强的 OCR。

先重建阅读顺序，认出标题、表格、图片、脚注。再按种类保住结构：表格留行列，图片留近旁文字和页内位置，正文留章节路径。入库存成可检索的块，块上带着父标题和原位置，种类分开切。Microsoft Azure AI Search 也是文档版面分析加结构感知切分，这是工程问题，不是纯面试概念。

本仓库：`parse_document` 产出段落 / 表格 / 图片 / 脚注 / 代码块，`chunk_blocks` 按种类切。块首是 `[p.3 / 差旅 / 住宿限额]` 这类路径。没有视觉模型，图只留下图注和坐标。

### 2. 一张表跨两页，还有多级表头、合并单元格，怎么解析和检索？

不能按页切。要看下一页是不是同一张表：列数相同、没有新的表题、第一行是重复表头或仍是数据，就拼回去。合并格按空单元格先向下再向右补。多级表头竖着拼成「部门 / 销售」。

检索分两步：表格摘要（标题、列名、行数）用来找候选表，结构化表用来取精确数字。涉及加减乘除时，本应交给确定性工具，不要让模型口算。本仓库检索仍只有 `retrieve`，数字留在 Markdown 表里给模型抄；要做汇总再加工具。

### 3. 已经用了 OCR 和大模型，复杂 PDF 的 RAG 为什么还不准？

OCR 主要解决「字是什么」，不保证阅读顺序、表格结构、图意和跨页关系。字全对，切分、检索、生成仍可能把证据切丢或拼错。所以要分开评：解析看行列和读序还在不在，检索看问数字能不能命中表块，生成看有表之后会不会算错或编造。

本仓库：扫描件带着识别框走同一条版面组装，不再 `join` 成一段再滑窗。解析用 `tests/test_parse.py` 看表头、跨页、分栏。检索和生成没有单独评测集，答错时先看切块再看召回，不要一上来换模型。

## 明确留到以后

| 问题 | 触发再做 | 倾向 |
|---|---|---|
| 版面启发式不够 | 双栏无沟、复杂版式、长乱码文本层开始砸人 | 换 LlamaIndex / 版面模型 |
| 表格计算 | 用户要汇总、对比，模型开始口算出错 | 检索仍找表，加减交给工具 |
| 父子块 | 小块能搜到，生成缺上下文 | 检索用小块，生成换上该块所在的节 |
| 按 token 切 | 要和某一家模型的窗口对齐 | 再上 tiktoken；现在和装上下文一样按字符估 |
| 重叠块近重复 | 前几名经常是同一段的两个窗口 | 相邻高分块合并，或重叠部分不单独计为新证据 |
| 文本层是长乱码 | 有字但全是错码，平均每页超过 40 字 | 现在不会改走识别 |

## 面试可以怎么说

块的大小是在「一条里要有完整事实」和「不要把无关句子嵌进同一个向量」之间取的。太长，问题只占块里一小段，相似度被冲淡。太短，事实被切成两半，哪一半都答不全。重叠是为了窗口边上的那句话两边都还在。代价是同一段会存成两块，检索可能连着命中。

Markdown 和 PDF 的麻烦在抽文本的时候结构已经丢了。标题路径、表格行列、阅读顺序、页眉，都得在切分之前保住。OCR 只保证字，不保证这些结构。

本仓库：先拆块再切。正文超长才滑窗；表格整段保留，跨页先拼，块里带摘要和行列。扫描件用识别框还原读序。块首写标题路径和页码。打不开、以及识别完仍没字的 PDF 直接拒绝。版面启发式不够再换 LlamaIndex。
