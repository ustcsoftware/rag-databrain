# 项目选型面试题

选型表见 [architecture.md](architecture.md)。切分的现实问题和本仓库做法见 [切分问题.md](切分问题.md)。后面加题：先对比「为什么业界这么选」，再一两句本仓库大致怎么做。不要堆接口字段、函数名。

## 1. 为什么流式用 SSE，不用 WebSocket？

Agent 项目一般都用 SSE。一次提问之后，只有服务端在推 token，客户端听完就断开。这和 SSE 匹配，和 WebSocket 不匹配。

SSE 还是 HTTP，只能服务端推客户端，发完请求挂着收流，结束就关。WebSocket 是双工长连接，两边随时互发，心跳、重连、消息协议都要自己管。Agent 这条链路是「问一次 → 模型边生成边吐 → 结束」，用 SSE 就够；只有同一条连接上人还要持续发（比如中途插话、协同）才需要 WebSocket。

本仓库：普通问答一次返回完整结果；流式另开 HTTP 接口，检索之后把模型的流式输出原样往下推，不把整张图跑完再吐。

## 2. 工作记忆怎么做，怎么避免撑爆窗口、追问检索不准？

多轮要把最近对话带上，否则「它」「再详细点」接不上。但不能把全部历史塞进模型：对话和知识库资料抢同一个窗口。

常见做法：滑动窗口只留最近几轮；对话设预算上限，闲聊不能挤掉检索结果；检索用改写后的独立问题，生成仍用原话加历史。整段聊天再 embed 进知识库、或先上 Mem0，都是下一档。

本仓库：请求自己带 history；最近几轮、最多占窗口三成。检索问句由循环里的工具参数写出。不落库。

## 3. Agent 循环怎么停？为什么不做成检索一次就生成？

Agent 要能多次行动再作答，一次检索不够时否则只能编或停。循环是：想 → 调工具 → 看结果 → 再想，直到直接输出答案。必须有步数上限，最后一轮禁止调工具，否则会死循环。相同检索问句不要再打一遍。

本仓库：检索是唯一工具；模型决定要不要再搜；最后一轮只生成。流式只推最终答案的 token。

## 4. 用户输入模糊怎么处理？

模糊分两档。省略和指代（「它」「再详细点」）靠上文能补全，检索前写成一句独立问句就行。真歧义是几种读法会搜到不同文档（「那个政策」「上个月的数」）。替用户挑一个意思，检索分数往往还不低，模型会顺畅地答错。

三档做法：

改写。把这一轮补成不看历史也能检索的问句，生成仍用原话和最近对话。成本低，多轮问答的默认项。它补的是「没说全」，补不了「两套都说得通」。

反问。几种读法对不上同一批资料时，这一轮先问清一个缺口，再检索。错文档配一段流畅回答，比多一轮对话贵。Agent 本来就可以不调工具、直接输出，澄清就是这一轮的答案。一次只问一个缺口。

多查询或 HyDE。一个问题拆成几条问句一起搜，或先写一段假想答案再拿去嵌入。解决的是用户用词和文档用词对不上，召回变宽。几路切片抢同一份上下文，互相矛盾的片段容易被揉成一个答案。探索式搜索合适；要对事实、库还小时不合适。

推荐改写加反问。改写处理接得上的模糊；读法会改变检索目标时反问，不猜。多查询和 HyDE 先不做：库小、窗口紧，它们加的是召回，不是消歧。等时间、主体、指标变成必填字段，再改成缺了就问。

本仓库：进循环前先判断。指代和省略补成独立问句，第一次检索用这句，生成仍看原话和最近几轮。几种读法对不上同一批资料时，这一轮只问一个缺口，不检索。判断结果读不出来就按原问题走原来的循环。没有多查询或 HyDE。
